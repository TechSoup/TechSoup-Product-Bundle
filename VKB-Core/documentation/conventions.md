# VKB Conventions — entry kinds

The VKB is broader than the Offer Center. It is a knowledge base of *support
for nonprofits* — today that's product **offers** (discounts and donations),
but it is meant to also hold **courses**, **services**, and other **resources**.
The Offer Center is just one consumer that renders a slice of it.

## The discriminator: `type`

Every entry's kind is declared by the OKF-required top-level **`type`** field in
its `<slug>_README.md` frontmatter. `type` is the single source of truth for
"what kind of thing is this," and every other naming decision keys off it.

Controlled vocabulary:

| `type` | What it is | Has an `x-civic.offer` block? |
|---|---|---|
| `offer` | A product discount, donation, or free/open-source deal | Yes |
| `course` | Training / learning | No (own shape, TBD) |
| `service` | Consulting, managed IT, fiscal sponsorship, etc. | No (own shape, TBD) |
| `resource` | Guides, toolkits, other support | No (own shape, TBD) |

Today every catalog entry is `type: offer`. New kinds are added by introducing a
new `type` value here first, then the feed/registry plumbing below.

### Agent & skill docs (not catalog entries)

Alongside the product READMEs, each category has an **orchestrator** and each
product an **entry agent** — the AI prompts that maintain the knowledge. These
are OKF concept documents too (they carry a `type`), but they are *not* catalog
entries and live outside the README:

| `type` | File | In a feed? | Schema-validated? |
|---|---|---|---|
| `orchestrator` | `<category>/*_orchestrator_skill.md` | No | No |
| `skill` | `<category>/<slug>/agent/*_skill.md` | No | No |

`build_products.py` and `validate.py` read only `*_README.md`, so these carry a
`type` for OKF §9 conformance but stay out of `products.json` and the civic
schema. (`skill` is one undivided type for now; subtypes can come later.)

### Index files (maps of content)

`index.md` files are OKF *listings* (§6), not concepts — generated by
`build_index.py` from the product frontmatter, one per category plus the bundle
root. They carry **no frontmatter except the bundle-root index** (§11), which
holds the bundle's `okf_version` and civic identity (`x-civic.namespace` /
`base_uri`). Don't hand-edit them; regenerate.

## One shared entry tree (Option A)

All entries live in **one** tree, discriminated by `type` — not split into
per-kind folders:

```
VKB-Core/products/<category>/<slug>/<slug>_README.md
```

A category (e.g. `fundraising`) can therefore hold an offer, a course, and a
service side by side. This keeps the VKB a single browsable knowledge graph so
recommenders and other tools can reason across kinds and relations. ("product"
is the legacy folder name; it now just means "the entry store." A future rename
to `catalog/` is possible but not required.)

## Naming keys off `type`

| Layer | Rule | Now | Later |
|---|---|---|---|
| **Registry** | one file per kind, in `registry/` | `offers_registry.csv` | `courses_registry.csv`, `services_registry.csv` |
| **Build feed** | one feed per consumer kind | `Offer-Center/products.json` *(= the offers feed)* | `courses.json`, `services.json` |
| **Consumer** | filters to its kind | Offer Center renders `type == offer` | each tool reads its own feed |

> **Legacy name kept on purpose:** the offers feed is `products.json` (not
> `offers.json`) because that is the live contract the deployed Offer Center and
> Azure Static Web App consume. Renaming it would break the deploy, so the
> asymmetry stands as accepted debt.

## The guardrail

`build_products.py` enforces the convention: `products.json` is built from live records
where **`type == offer`** only (records with no `type` are treated as offers for
backward compatibility). A future `course` or `service` therefore cannot leak
into the Offer Center — it will be skipped by type and must be emitted to its
own feed.
